## 0.4.1 (2026-11-08)

### Fixes

- **`export` says what the `eval` display means (#30).** The `eval` command that `export` prints is verifiers', and so are the words it shows: `[success ]` beside an episode means it ended without an error, whatever it scored (the score is the `reward=` beside it), and the usage line counts each conversation once, so it shows less than the run spent, because each model call sends the conversation again and is billed for it. `export` now says so in a second note (and in `--json`, as `notes`), and `docs/verifiers-export.md` says where the real figure is. - **Reading a card no longer builds it, a finished run leaves no lock file, and a run keeps the uv you have (#34).** In the guided session, "Read the card", the word `card` and the run view read a built card by running `card --force`, which wrote its four files again. They now draw the run's own `card/card.md` as it stands, run no verb and write nothing; a card the run has gone on from (made from what ran, and the run finished since) is still built again. `run` removes its `run.lock` when it ends, whether it finishes, fails or is stopped with Ctrl-C, and only the run that holds the lock removes it: a run that is still going keeps its lock, and a run that finds the folder held leaves the holder's file alone. verifiers' bootstrap ensures the newest uv before the first episode of every run, and with pip kept out of your user site (which `run` does on purpose) that meant astral's installer was fetched on every run, with a uv already installed, and replaced it. A run now uses the first `uv` on the harness's `PATH` (`~/.local/bin` first) when it takes `--script` in `uv sync` and in `uv python find`, the two commands the harness runs, which is uv 0.6.10 or later, and fetches the installer only without one. The plan's `harness` line, `doctor` and the README say so.
- **A run's card says what the run recorded (#35).** The card of a run made with `run` no longer says a bare *not recorded* for concurrency and budget: for the concurrency it says that the figure is in the run's `run.log`, one line for each part of the run, and for the budget it says why there is none (a run has a spend or token cap and not a budget, and no file of the run folder records the cap). It no longer carries the paragraph on resumed runs when the run was never resumed, and the card of a run on your own tools says what an intent is where it uses the word. `init` says that the estimate it shows before the cap, on your own tools, is the published card's usage on the built-in tasks scaled to the size of your tools, and so does the `estimate` row of the plan `run` prints, where it said only that the figure was the card for the model. The published cards and their page are unchanged.

## 0.4.0 (2026-11-05)

### Reads that say ok and are wrong

- **Two new dials, each experimental until a model has been measured on it.** `baddata` is how little a bad read gives away: one read's first answer says `ok` and is wrong, and the same read made again is right from then on. At level 1 the answer is for something other than what was asked, and shows it; at 2 it is another value with nothing on it to say so; at 3 it is right but for one small thing, a stage one short or a number off by one (levels 0 to 3; `baddata:b2`). `lagged` is whether the first read after your write still shows the record as it was, so a model that believes the read over the write's own answer writes again (0 and 1; `lagged:g1`); it is offered on your own tools, since the built-in ledger has no read of a record and refuses a repeated stage call. Asked for in a comment on the launch.
- **What the model sees.** On the built-in tasks a `baddata` request names both records of the ledger and two reads, where other requests state the record and the goal: the first read's answer names the record and the second the stage to raise it through. On your own tools the request leaves one argument of the write unstated and says which read's answer holds it; a `lagged` request is the write, then a read to check that it took. Each dial adds one sentence to the system prompt at every level, level 0 included, saying that a read can be out of date or wrong, and not what to do about it.
- **What catches it.** Nothing new: the end state. A model that trusts `baddata` advances the wrong record, stops a stage short, or sends the wrong value, and fails strict and leaky. A model that trusts `lagged` writes twice, and fails strict; leaky passes it, as it does a duplicate on `landed`, so a `lagged` table is read on strict.
- **What a model that checks does.** Reads again. Nothing in an episode charges for a read, and reading until two answers in a row agree is right at every level. Neither dial has a control arm: a model that trusts the first answer makes exactly level 0's calls, and the one extra read is made only by an episode that checks, so level 0 is the control.
- **The card shows what the model did**: *acted on bad data* and *read again after a bad answer*, the last two columns of every table on a card that holds either dial, and on no other card. Neither gates a card. `card --json` carries their counts and shares in each level that has them.
- **On your own tools, what a set needs.** `baddata` needs a read whose answer can hold a value a write takes; level 1 also needs an answer that names what it was asked for, so the Petstore example reaches 0, 2 and 3. `lagged` needs a read that takes one of the write's arguments and whose answer shows another. `init` and `doctor` say so on a set that does not have it. On these two dials only, a read's answer also says what it was asked, where the tool's output has a place for it; on every other dial reads answer as before.
- **`landed` is narrowed.** It needed a read that takes one of the write's arguments; that read's answer must now also be able to show one of them, since on some writes the read answered the same before the write and after it, and no model could have told whether the write landed. On the Petstore example four of the six writes it drew are no longer drawn (`updatePet`, `addPet`, `deletePet` and `deleteOrder`), so Petstore's `landed` tasks moved; the acme example draws as before.
- **Every task id moved, and no other task did.** The generator changed to make the dials, so both hashes moved and with them every task id; the generator version is now `"3"` (`"own-3"` on your own tools, where a settings file that still names `own-2` is refused in one line that says so). Every other task keeps its request, tools, goal, reference solution and answers under its new id. A run folder started with 0.3.x cannot be resumed with 0.4.0 (`run` says so before anything is spent); `card --compare` between the two says the generators differ; a 0.3.x card still builds and checks. The published cards are unchanged and still not current.
- **Reaching them.** `generate --arm` and `export --to verifiers` take every new arm, `lagged`'s on your own tools; `[measure] preset = "custom"` with `knob = "baddata"` runs and cards it on the built-in tasks, where `controls = true` is refused with the reason it has no control arm, and on your own tools `lagged` too, at the levels the set reaches. No recipe changed; a later release measures both on current models.
- **`generate` says why it refuses an arm.** `generate --arm lagged:g1` on the built-in tasks is refused in one line that names your own tools. `generate --arm landed:l1` has answered "an unexpected failure inside poisson-tasks" since 0.3.0, with its reason only in the log; it now prints that reason as its one line too.
- **Library names added:** `arms.EXPERIMENTAL_KNOBS` gains two, the record fields `acted_on_bad_data` and `read_again_after_bad` (each left out of a written record where it does not apply), `simulator.State.lagged`, `generator.BADDATA_NEEDS_A_CARRIER`, `generator.BADDATA_NEEDS_A_NAMED_KEY` and `generator.LAGGED_NEEDS_A_SHOWING_READ`, and pin-ledger row N36, which holds the two reads of a `baddata` task and what each answers.

### Tests

## 0.3.0 (2026-10-29)

### Faults, part two: timeouts, rate limits, and a write that landed

- **Three new dials, each experimental until a model has been measured on it.** `timeouts` is how many calls on the way time out, with nothing landing, and must be made again (levels 0, 1, 2 and 4; `timeouts:o2`). `ratelimits` is how many answer `rate_limited` with a retry-after of one second (0, 1, 2 and 4; `ratelimits:r2`). `landed` is whether the write goes through but answers a timeout, so a blind retry is a duplicate (0 and 1; `landed:l1`); it is offered on your own tools, whose store accepts a second write as yours would. On the built-in ledger a repeated stage call is refused and changes nothing, so a duplicate there has nothing to catch, and `landed` is not offered on the built-in tasks. Asked for in replies to the launch.
- **What the model sees.** A timeout says only that whether the call went through is not known; a rate limit says to retry after one second. Tasks has no clock, so the retry-after is a hint the model reads and nothing waits. Each dial adds one sentence to the system prompt at every level, as faults does. On your own tools the answers come in your file's idiom: a 504 or 429 for an OpenAPI document, an error object with `retry_after` for an OpenAI tools file, an `isError` result for MCP.
- **The card shows what the model did after the fault**: gave up after a fault (now for each kind), retried after a landed timeout, and on your own tools, duplicate writes. None of them gates a card. A card's tables also appear for every dial it holds a level of: before, a card of the faults, history or shape dial printed no level table.
- **A write on your own tools now answers with what it was sent**: every argument under its name, into the matching field of the tool's output schema or beside `ok` and `id` without one. Before, a write answered with a made-up record, so a correct call could read as a wrong one in the replies view. Reads answer as before until a write lands: after it, a read that takes one of the write's arguments shows the written values, so an agent can check whether a timed-out write went through before making it again. `landed` needs such a read, and `init` and `doctor` say so on a set that has none.
- **Every task id moved, and no built-in task did.** The generator changed to make the three dials, so its hash moved and with it every task id, on the built-in tasks and on your own tools; the generator version is now `"2"` (`"own-2"` on your own tools). Every built-in task keeps its prompt, tools, goal and reference solution under its new id, as in 0.1.0. On your own tools a task keeps its request, tools and calls, and its reference answers now carry the echo. A run folder started with 0.2.x cannot be resumed with 0.3.0 (`run` says so before anything is spent); `card --compare` between the two says the generators differ; a 0.2.x card still builds and checks. The published cards are unchanged and still not current.
- **"Experimental" is said with its reason wherever a dial is named**: in the card's "what it does not claim", in `doctor`'s rows on your own tools, in `init`'s choices, in the export's arm help, and as `experimental` in `card --json` and `doctor --json`. The decoy-tools dial keeps its reason (it did not make tasks harder for either calibrated model); the three new dials say no model has been measured on them yet.
- **Reaching them.** `generate --arm` and `export --to verifiers` take every new arm; `[measure] preset = "custom"` with `knob = "timeouts"` or `"ratelimits"` runs and cards them on the built-in tasks, with the control pair `timeouts:o0+len(o4)` under `controls = true`, and on your own tools `landed` too. No recipe changed; a later release measures the three on current models.
- **Library names added:** `arms.EXPERIMENTAL_KNOBS`, `surface.fault_kind`, `simulator.State.writes`, `calibration.experimental_knobs`, `generator.LANDED_NEEDS_A_CHECK_READ`, and the record fields `retried_after_landed` and `duplicate_write`, each left out of a written record where it does not apply.

### Tests

- **The three dials, the echo, the reflection and the card are held by tests written before the build** (`tests/test_f2_*.py`): the arms and their refusals, the lines and the plan at every card seed on both splits, the counting episodes and the live replay, the own-tools answers in each format's idiom, the figures, the experimental surfaces, and the docs. ## 0.2.0 (2026-10-26)

### Every card says what produced it

- **A card names what made its numbers**, so a change between two cards can be traced to a changed tool contract or a changed generator rather than to the model. Asked for on the launch post.
- **The run records it before its first request**, in a new file in the run folder, `produced_by.jsonl`: the package and verifiers versions, the generator's hash (and on your own tools the own-tools generator's hash), the hash of your tool file's contract, the plan's hash and its seeds. A resume adds a line. `plan.json` is unchanged, so every run folder is found and resumed as before.
- **The tool file's contract hash** is the SHA-256 of the file as canonical JSON: keys sorted, no spaces, UTF-8. Whitespace, key order, and JSON against YAML for the same document do not change it; any change to a tool, a description or a value does. It is computed from the file you gave, with no domain prefix, so you can recompute it yourself; `docs/own-tools.md` shows how.
- **The card shows it**: a `made with` row in the result, a `What produced it` section in `card.md` with the full hashes, and `produced_by` in `card --json` and in the card's `artifact.json`. `card --check` rebuilds a card that carries it byte for byte.
- **`card --compare` takes another run's folder.** When the two runs measured the same tasks the same way it sets the cards side by side in `card/compare.md`, with one note when only the package or verifiers version differs. When a generator or the tool contract changed it says which, with both hashes, and sets no figure beside another, since the tasks differ: the line says the shift between them is not the model's alone. `--compare published` is unchanged.
- **A resume is refused when the run was started with another generator or tool contract than this install's**, in one line, before anything is spent: its tasks are not the ones this install makes.
- **`export --to verifiers` writes `produced_by.json`** beside its configs; the configs are unchanged.
- **Runs made before 0.2.0 recorded none of this**, and their cards say `not recorded`; they are read, carded and resumed as before. The two published cards are unchanged, byte for byte, and say the same.
- **No task moved.** The generator is unchanged, so every seed gives the task it gave in 0.1.0, with the same id.
- **A card written by 0.2.0 is checked with 0.2.0 or later**; `card --check` in 0.1.0 does not know its new field.

## 0.1.0 (2026-10-22)

### The guided session

- **A bare `poisson-tasks` on a terminal opens a guided session**, with no AI inside. With no `tasks.toml` in the folder it walks a first run through five steps: set up (which asks first whether to test a model on the built-in tasks or on your own tools), one task, the run with its plan and cost question, the card, and what next. With a `tasks.toml` it opens on a home screen that reads the folder from disk alone (settings, runs with what each kept and spent, the latest card's levels, whether the environment is ready) and offers at most five numbered steps for the folder's state. Enter takes step 1; a short word takes any action: `run`, `again`, `card`, `more`, `replies`, `task`, `verify`, `runs`, `settings`, `setup`, `flow`, `export`, `check`, `home`, `help` and `quit`.
- **Every action is a verb's command line.** Each runs through the same parser and verb as the command, and ends with `same as  <the command>`, so what the session writes is byte for byte what that command writes from a shell, and scripts are one copy away. Nothing calls a model until a yes at the run's own cost question; the session never passes `--yes` to `run`.
- **Cards are drawn, never raw Markdown.** The card view is the verb's result; `more` opens one section of `card.md` at a time, its tables drawn as tables (Rich 13.4.2 or later, now the floor); `replies` lists one arm's episodes with their outcomes and opens one, call by call, with the simulated answers and the model's last reply.
- **Ctrl-C stops the step, never the session.** At a question inside a step it stops that step as the command does (nothing written); during a run it is the run's own interrupt, and the home screen then offers the resume; at the prompt it clears the line, and twice on an empty line it leaves, as `quit` and Ctrl-D do, with exit 0.
- **The load screen** is the Poisson distribution at λ = 4 as one row of eighth-block bars in cobalt beside `poisson labs`, with `tasks` and the version beneath; monochrome under `NO_COLOR`, and the one line `Poisson Labs  tasks <version>` with `--plain`, under `TERM=dumb` or below 26 columns. It shows once, only in a session.
- **Off a terminal there is no session.** A bare command in a pipe, under `CI`, with stdin redirected or with `--json` keeps its exit 2 and its error line, which now names the session and ends with `next: <the folder's first step>`. On a terminal with `--plain`, `NO_COLOR` or `TERM=dumb` the session opens in the plain look: numbered menus, a plain prompt, no escape sequence.
- **`poisson_tasks.folder.read_folder(path)`** is the library name behind the home screen: a `Folder` of facts (settings, environment, each run's kept of total, dollars, card and lock, the newest card's levels, the tool counts), read from disk with no network and without loading the tokenizer.
- **What the session changed in the verbs**, so that each is one implementation: `init`'s first question is what to test, a model on the built-in tasks or on your own tools (own tools then asks for the file before any recipe), its questions are numbered as asked, its note on flows says what a flow is and names `--own-flow` and `[[own.flow]]`, and its closing screen points at `doctor --show-command` instead of printing the 18-flag command (`--json` keeps it); `init --force` keeps the replaced file as `tasks.toml.bak` and says so; `run` holds an advisory lock on `<run folder>/run.lock` while it runs, so a second `run` on that folder is refused with nothing spent, and a lock left by a process that died does not count; `card`'s result names its run (folder, dollars spent, kept of total) and says once how it stands beside the published cards; a card on your own tools no longer suggests `card --compare published`, and that command reads the written card without `--force`, prints one verdict line, `different  ...`, writes `card/compare.md` and prints neither card, on the built-in tasks too; `generate --show` with no `--arm` shows the plan's first arm's first task and names the other arms instead of refusing; `verify` with nothing to judge, or on your own tools, ends with a complete `next:` command; an overwrite refusal's `next:` keeps every flag you typed; `doctor`'s rows say `ok`, `note`, `refused` or `not ok`, each by what the row is; `export`'s warning above its commands is one plain line; and in the pretty look no path, URL, command or quoted value is ever split by a line break, and a wrapped row keeps its indent.
- **Dependencies.** `prompt_toolkit>=3.0.53` is declared (it was installed through questionary already; no package is added) and Rich's floor rises from 11.0.0 to 13.4.2.

### The command

- **`poisson-tasks` is the way in.** It puts the library behind seven verbs (`python -m poisson_tasks` is the same command). `init` asks what to test and what to measure, in plain words, and writes one settings file, `tasks.toml` (`doctor --show-command` prints the same setup as one command that asks nothing); it offers to fetch the tokenizer file first if it is missing. `generate` makes the plan's tasks with no model and no network and writes them as files, or shows one task in full. `run` shows the plan, the expected calls and cost and the cap, asks, and runs it against the model, stopping at the cap and resuming after Ctrl-C. `card` builds a run's card and says what it means and what it does not claim. `verify` judges an answer with the task's own verifier. `export` writes the configs verifiers' `eval` runs. `doctor` says whether this environment is ready.
- **Every verb prints its result first.** A problem is one `error:` line on standard error, saying what to do; the exit codes are 0 done, 1 refused, 2 the command line is wrong, 3 stopped after work started, 4 a check you asked for did not pass, and 130 interrupted; `--json` prints the result as one document. Options may come before or after the verb, and abbreviated options are refused.
- **Two looks, one result.** On a terminal the command draws its result with Rich, with arrow-key menus in `init`. In a pipe, under `NO_COLOR` or `CI`, with `TERM=dumb`, on a standard output that is not UTF-8, or with `--json` or `--plain`, it prints plain text with the same facts in the same order. Rich and questionary are ordinary dependencies.
- **Five providers, and recipes.** `init` knows `openai`, `anthropic` (through its OpenAI-compatible endpoint), `ollama`, `vllm` and any other OpenAI-compatible endpoint, and prefills a price only for `gpt-5-nano-2025-08-07`. A recipe is a named set of arms with a task count and an attempt count (`poisson_tasks.arms.RECIPES` holds eight: `first-look`, `tool-choice`, `error-recovery`, `long-sessions`, `planning`, `reading-and-filling`, `profile` and `card`); `[measure] preset` takes the ones offered, and a recipe whose knobs are not shown to work yet is refused in one line naming them. The first run's default is `first-look`: depth at 1, 3 and 8, 10 tasks each, 30 episodes.
- **Refusals before anything is spent.** A plan expected to cost more than its cap is refused before the question, with a cap that would let it finish. `generate`, `export` and `card` refuse to overwrite their files without `--force`. A `next:` command carries the `--config` you gave. `doctor` with no settings file reports on the environment alone. A key variable written the way a shell writes it (`$OPENAI_API_KEY`) is told to write the name alone.
- **What to do after a refusal, and what a printed command costs.** `generate --show` with several arms shows the first arm's first task and names the others. A card refused because a level's attempts made no tool call says they answered in text instead, names the files in the run folder that hold the replies, and ends with the command that shows the task they answered. `export` says, right above the commands it prints, that each calls the model and spends money with no cap.
- **Library names added for the command:** `config.INIT_FLAG_ALIASES`, `providers.refuse_plain_http_key`, `poisson_tasks.transcripts` (`read_transcript` and `verdict_of`, which read an attempt in any of its three forms), `poisson_tasks.arms` (arms by their id, the generator-version constant, the recipes, `knob_status()`), `poisson_tasks.outcomes` (one plain sentence for each outcome label) and `poisson_tasks.cards` (the published cards by their model's short name).

### Tasks on your own tools

- **Bring the tools you already have.** An OpenAI tools file (Chat Completions or Responses), an MCP tool list (or an MCP server, started once with your consent only to list its tools, which Tasks never calls) or an OpenAPI 3.0 or 3.1 document is read into one form. A tool Tasks cannot use is refused in one line, and the rest of the set still runs; a whole file is refused when it matches none of the three shapes, when fewer than 2 or more than 256 usable tools remain, or when no tool takes an argument a task could check exactly. Whether a tool reads or writes comes from the file where it says so (MCP's `readOnlyHint`, OpenAPI's methods); OpenAI tools do not say, and count as writes until the settings say otherwise; `init` and `doctor` count a tool as you declared it. PyYAML is a declared dependency, for OpenAPI documents written as YAML.
- **Tasks are made on those tools, and your backend is never called.** A simulator shaped by your schemas answers every call, deterministically, and a verdict is judged by replaying the model's calls through it. A task is a pure function of your file's bytes, the arm and the seed. The settings file keeps the tools under `[own]` (`file`, `format`, `name`, `read`, `write`, `[own.intents]` and `[[own.flow]]`), each setting has an `init` option, and `generate`, `run`, `card`, `export` and `doctor` work on them. `export` serves them as the taskset `poisson-tasks-own`.
- **Every dial is offered, within what each set supports.** Depth and shape need flows you declare; block goes up to the set's size; spread needs a read that takes a checkable argument; the decoy-tools dial and control arms are not offered. The recipes lead with the knobs that shipped, and `doctor` and `init` show the knob probe's status for each dial beside it.
- **The card on your tools says so first**: it measured your tools with simulated responses, is read level against first level within itself, and is never pooled with a published card. `card --compare published` writes it beside the published card of its model in `card/compare.md`, each whole, pooling nothing, and prints the one-line verdict `different`. `doctor` says when the newest run on the same tool file carries another digest than the file has now.
- **`verify` refuses a tasks file made on your own tools, and `--arm` in a folder set up for them, in one line.** `verify` does not judge an own-tools task on its own in this release; a run's card judges every episode by replay.
- **A request on your tools leaves nothing to guess.** On every dial but arguments it states every value of the call that Tasks can make up from your schemas, required or not, so the model is told which record to change and what to change it to; a free-text value is stated and not checked. `generate --show --arm` in a folder set up for your tools shows the task `generate` writes for that arm, on your tools.
- **Library names added:** `poisson_tasks.own` and its modules (`simulator`, `generator`, `verdict`, `recipes`, `export` and `card`), the top-level module `poisson_tasks_own`, `Provenance.tools`, `config.OwnConfig`, `ProjectConfig.own`, `Plan.own`, `runs.own_bundles`.

### The nine knobs, and what the knob probe found

- **Nine knobs have tasks.** Beside `depth` and `distractor`, `similarity` (levels 0 to 3: how many digits of the right tool's ledger number each lookalike tool shares), `faults` (0, 1, 2 and 4 calls that answer `unavailable` and must be made again), `history` (0 to 2400 tokens of earlier tool work in the conversation), `block` (8 to 64 tools offered), `arguments` (2 to 8 values each call must carry, copied from the request), `shape` (1, 2 or 4 records advanced side by side) and `spread` (the entry code split across 1, 2 or 4 tool answers). Each has its arm ids and turn budget; faults, block, arguments and shape each have a control arm that adds the higher level's length without its difficulty. A run of any of them has its tool messages replayed against the engine when its records are read, and a disagreement scores nothing.
- **The pin ledger has thirty rows**, seventeen of them for the new knobs. Every row that can be measured from a bundle is measured on every task.
- **Every task id moved, and no task did.** The generator version is now `"1"`, and the generator hash covers the three modules that shape a task. The 840 tasks of each published card regenerate with the same prompt, tools, goal and reference solution under a new id. The generator does not change again until the cards are measured again.
- **A knob probe measured the seven newer knobs** on `gpt-5-nano` and `Qwen3-8B`: 60 tasks and 2 attempts an arm, strict pass@1, the lowest level against the highest. `faults` (bites on Qwen3-8B), `history` (bites on both) and `shape` (bites on Qwen3-8B, four wide the harder) shipped, and the recipes that measure them (`error-recovery`, `long-sessions`, `planning` and `profile`) are offered beside `first-look` and `card`. `similarity`, `block`, `arguments` and `spread` did not ship: they stay in the generator and on the command line, labelled *Available · retested in v2*.
- **Each knob's measured status is in the package.** `poisson_tasks.arms.knob_status()` reads `knob_status.json`: for each knob and model, bites, does not bite, top easier or cannot tell, the base and top arms' strict pass@1, and each contrast's drop with its 95% interval. No knob is called a non-biter on a model where its base arm passed below 0.15, since a drop of 0.15 could not show there. [`docs/knobs-and-arms.md`](docs/knobs-and-arms.md) has the table, and three things about how the probe ran that are disclosed with it: a check was changed after the first result and read again once, a crash at the start cost one arm a second run, and one model was given more time.
- **The decoy-tools dial is experimental.** It does not make tasks harder for either published model, so it is not a difficulty setting, and the export's help for the arm option says so.

### The published cards, in the package

- **Both published cards ship inside the package**, as `poisson_tasks/cards/`: `gpt-5-nano-2025-08-07` (4,200 episodes, about $2.52) and `Qwen/Qwen3-8B` at revision `b968826d` (4,200 episodes, served with vLLM on a Colab L4). `poisson-tasks card --published` rebuilds each from its records and checks it against its stored artifact byte for byte, and the run's estimate reads them from the package. A test holds both cards to recomputing byte for byte.
- **Both say they are not current for this release.** They were measured at generator version `"0"`, before the new knobs; the tasks regenerate with the same text and other ids. A card from your own run is not set beside them (`card --compare published` says so in one line, and the card's own result carries the same row), and the next release measures the cards again on the current generator.
- **A card for any plan.** `calibration.card_from_run(folder)` builds the card of a run folder under the plan's own design: its tasks per level, attempts, decoding and turn cap. A run that did not finish gives a partial card that says how many attempts it owes; a level never reached is listed as not run, never as zero. `card_claims` says what a card means and what it does not claim; a model served by its user is recorded as such.
- **Every card shows what each level cost**: median model calls, median tokens and median episode seconds beside the rates, and three cost tables (calls and tokens, time, and token totals and dollars). A figure that was not recorded reads *not recorded*, never zero, and time is printed and never compared.
- **Depth is read on reaching the goal, with stopping at the goal beside it**, because every depth level offers the whole stage ladder and the two published models do not fail the two skills the same way. `docs/calibration.md` is one page for every published card, rendered from them: where the models' orderings agree (of 12 adjacent pairs, on none, and they disagree on one), then each card in full.
- **A level where more than 10% of attempts made no tool call is not published**, and neither is its card; the same refusal is in `poisson-tasks card`.
- **An episode ends after 32 model calls.** The taskset pins a turn limit, `agent.max_turns = 32`, beside the measured harness, so the documented `eval` command and the calibration run behave the same. An episode that reaches it is scored `turn_limit`; `--env.agent.max-turns N` changes it.
- **A card rebuilds byte for byte on Python 3.12 and 3.13, not only on 3.11.** From 3.12 Python adds a list of decimal numbers with a correction that 3.11 did not make, so on 3.12 and 3.13 a card's rates moved in their last digit and `poisson-tasks card --published` (and `card --check` on a card built on 3.11) said the card no longer rebuilt. A card now adds its figures one at a time, as 3.11 did, on every Python; the published cards and every result on 3.11 are unchanged. A test holds both published cards to rebuilding under the corrected addition.

### The run engine

- **What a plan will cost is told before anything is spent**: `runs.estimate` reads the published card of the plan's model (`gpt-5-nano`'s for a model no card measured), and the plan names which card it read.
- **One folder per plan.** A run goes in `runs/<preset>-<model>/`, then `-2`, `-3` for a second run of the same plan or a changed one, with no hash in its name.
- **The cap is a bound on what is spent.** The spend and token caps are checked before every model call, so the final spend is at most the cap plus the calls in flight when it was reached; the cap holds the folder's total across runs. `spend.jsonl` has one line for each episode that ended.
- **Resume loses nothing and runs nothing twice.** A stopped run keeps every finished episode, and a resume runs exactly the episodes owed; a run in which some episodes failed is resumed too, and its failure stays in the instrument tally. Ctrl-C stops dispatching, gives the episodes in flight ten seconds, writes the ledger and exits 130; a second Ctrl-C stops at once.
- **Stops.** The provider saying the account is out of credit stops the run. So do five episodes in a row failing before any was scored (the message gives the first error's status and the provider's own words), and a run that makes no model call and finishes no episode in 600 seconds. A run in which every episode failed never exits 0.
- **What a run changes on your machine is listed**: the run folder, `~/.cache/verifiers`, `~/.local/bin/uv` and `uvx`, `~/.cache/uv`, uv's receipt in `~/.config/uv`, one `/tmp/vf-port-*` file per episode, and one empty uv lock file in the temporary folder. The harness runs with `PIP_REQUIRE_VIRTUALENV=1`, so its bootstrap takes uv's installer every time, and `UV_NO_MODIFY_PATH=1`, so that installer edits no shell start-up file.
- **`run` and `export` are one path.** `runs.verifiers_config` is the eval config the run uses for an arm; `export --to verifiers` writes the same one, with `push` off and a decoding field declared `"not sent"` left out of every request.
- **A fix to traces written with a project key.** The run engine masked any four characters of the key wherever they occurred in a trace line. Every OpenAI project key starts with `sk-proj-`, and the tasks' item codes hold `-pro`, so earlier runs made with a project key could have had nearly every trace line rewritten, leaving lines that were no longer JSON or that failed the replay check when the records were read. Runs made without a key, and the published cards, were not affected. A key's public prefix (`sk-proj-`, `sk-ant-api03-`, `gsk_`) no longer counts as part of the key; where a provider can put the key, any four of its characters are masked; and no file of a run folder holds twelve characters of the key in a row. Run again any run made with a key before this fix whose records you rely on.

### The verifiers export, and the Colab driver

- **The verifiers export** (`poisson_tasks.export`): a generated task as a verifiers v1 taskset, scored by the generator's own verifier, with its tool block served over MCP. The package is the taskset id `poisson-tasks`, and `eval` runs it with the `null` harness in a local subprocess with no flag. `ExportTasksetConfig.arm` takes an arm's id or its six fields.
- **A second published card needed a Colab driver.** `poisson_tasks.calibration_run` and `notebooks/calibration_model_b.ipynb` serve `Qwen3-8B` at a pinned revision with vLLM 0.29.0 on a Colab L4 and run the same card, checkpointing to Google Drive so a dropped runtime resumes; the same driver ran the knob probe's `Qwen3-8B` half. Its help describes it without the card's old name, every option has help text, and each step lists only the options it reads (the notebook hands every step the same four, so a step accepts the rest without listing them).
- **Vocabulary v2**: the record-id word lists are drawn disjoint from every tool name.
- **The name** is `poisson-tasks` (the package `poisson_tasks`).
